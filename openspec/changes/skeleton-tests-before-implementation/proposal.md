## Why

The schema tells an agent to *promote* integration and E2E skeletons
(`templates/tasks.md` groups 4 and 5) but no task group ever creates them: group
1 declares contract stubs, group 2 writes unit tests, group 3 implements. An
agent following the template faithfully therefore has nothing to promote, and
resolves the contradiction the cheapest way — by creating the test file after
the implementation it was meant to guard, which is exactly what BR-4 forbids and
what BR-7 predicts. This was found by reading a downstream change generated by
this schema, where the E2E skeletons were authored in group 5, two groups after
the code.

The same gap hides itself: the Integration and E2E tables in `test-plan.md`
carry only a current `Status` column, so a change that wrote its tests last ends
with a table indistinguishable from one that wrote them first (BR-6).

## What Changes

- Add a task group for integration and E2E skeletons **before** the
  implementation group in `templates/tasks.md`, and renumber the groups after it.
  Groups 4 and 5 keep their "promote" wording, which becomes true rather than
  aspirational (BR-4, BR-7).
- Restate the group order in the `tasks` artifact instruction in `schema.yaml`
  so the sentence an agent reads matches the template it fills, and say
  explicitly that implementation must never be the step that first creates a
  test file (BR-4).
- Add an `Initial Status` column to the Integration Tests and E2E Tests tables in
  `templates/test-plan.md`, and require it in the `test-plan` artifact
  instruction (BR-6).
- Derive the archive gate's pending-test list from a table's live `Status`
  column, falling back to `Initial Status` only when a table has no other. Today
  every status column feeds that list, so an `Initial Status` of `skeleton` that
  ended `passing` would be reported as an unowned skeleton — a false positive the
  new column would otherwise introduce (BR-5).
- Warn when an Integration or E2E row leaves `Initial Status` empty. New
  invariants start as warnings in this kit, so this does not block an existing
  change mid-flight.
- Document the ordering in `docs/openspec-okf-workflow.md` §7.

Not breaking: a `test-plan.md` written against the old template keeps validating,
and gains one warning per unfilled row.

## Capabilities

### New Capabilities

- `test-first-gate`: when each level of test must exist relative to the
  implementation it guards, the status vocabulary that expresses it, and how a
  test-plan proves the order was honoured after the fact.

### Modified Capabilities

None. The archive gate's requirement — no skeleton archived without an owner —
is unchanged; only which column answers "is this row still a skeleton" changes,
and that is test-plan semantics, owned by the new capability.

## Scope And Non-Goals

**In scope:**

- `openspec/schemas/okf-gated-feature/templates/tasks.md`
- `openspec/schemas/okf-gated-feature/templates/test-plan.md`
- The `tasks` and `test-plan` artifact instructions in
  `openspec/schemas/okf-gated-feature/schema.yaml`
- `lib/check.mjs` test-plan checking
- `docs/openspec-okf-workflow.md` §7

**Non-goals:**

- Enforcing the ordering itself. `okf check` reads finished files and cannot
  observe when a file was created; it can only require that the initial status
  be recorded, and make an absent record visible. Claiming otherwise would be a
  gate that cannot fail.
- Retrofitting changes already archived, or the downstream change that surfaced
  this. Their `tasks.md` files are historical records.
- Touching the `okf-*` capabilities or any generated skill file under
  `.claude/`, `.codex/`, `.cursor/`.

## Acceptance Criteria

1. `templates/tasks.md` contains a group that creates integration and E2E
   skeleton files, positioned before the implementation group, and every group
   after it is renumbered consistently (BR-4).
2. No artifact in the schema instructs an agent to promote a skeleton without an
   earlier instruction that creates one (BR-7).
3. The group order sentence in the `tasks` instruction in `schema.yaml` lists the
   same groups, in the same order, as `templates/tasks.md`.
4. The Integration Tests and E2E Tests tables in `templates/test-plan.md` each
   carry an `Initial Status` column alongside the current `Status` column (BR-6).
5. A test-plan whose Integration or E2E row has an empty `Initial Status` cell
   produces a warning, not an error, and not silence.
6. A test-plan row whose `Initial Status` is `skeleton` and whose `Status` is
   `passing` does not require a Known Gaps row at archive time (BR-5).
7. A test-plan row whose `Status` is `skeleton` still requires a Known Gaps row
   with an owner at archive time — the existing behaviour is unchanged (BR-5).
8. An unknown word in either status column is still an error (BR-1).

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| The skeleton group becomes a box-ticking step: files created, then rewritten wholesale after implementation | The ordering looks honoured while nothing was refuted | The template names the promotion step separately, and BR-6 keeps both statuses visible; beyond that this is a review concern, not a mechanical one |
| A downstream project's runner has no pending mechanism | The skeleton status cannot be expressed | Recorded as an assumption in the OKF entry; such a project states the reason under Test Strategy like any other non-applicable level |
| Renumbering task groups breaks a downstream change mid-flight | An in-progress `tasks.md` no longer matches the template | Templates are read at creation time only; an existing `tasks.md` is never re-derived |

## Impact

- `openspec/schemas/okf-gated-feature/schema.yaml` — `tasks` and `test-plan`
  instructions
- `openspec/schemas/okf-gated-feature/templates/tasks.md`,
  `templates/test-plan.md`
- `lib/check.mjs` — `checkTestPlan`
- `test/run.mjs` — new cases for the live-status column and the empty
  `Initial Status` warning
- `docs/openspec-okf-workflow.md`
- No CLI surface change, no dependency change. Downstream projects pick this up
  by upgrading the schema; changes already in flight are unaffected.
