# OpenSpec + OKF workflow

Three things in this repository describe one feature, and they must agree:

| Layer | Lives in | Holds |
| --- | --- | --- |
| Knowledge | `.okf/features/<capability>.md` | Domain terms, actors, permissions, workflows, and business rules with stable ids |
| Requirements | `openspec/specs/<capability>/spec.md` | Requirements and scenarios, which cite rule ids instead of restating them |
| Behavior | the code and its tests | What actually runs |

Keeping them in sync is the one non-negotiable. Everything below exists to make
that cheap: a small change takes a short route, and only a change to what the
knowledge says goes through the full OpenSpec workflow.

The full workflow is defined by the `okf-gated-feature` schema
(`openspec/schemas/okf-gated-feature/schema.yaml`) and `openspec/config.yaml`.
The `openspec-*` skills under `.claude/`, `.agents/` and `.cursor/` are
regenerated by `openspec update` - never hand-edit them. Everyone uses the same
OpenSpec version, because those files are generated for it:
`npm i -g @fission-ai/openspec@1.14.3`.

## Business rules and `BR-n`

A business rule is a statement the domain requires to be true, for example
"an order holds at most 5 items". Each one is written once, in the capability's
OKF entry, with a stable id: `BR-1`, `BR-2`, ... Specs (`Implements: BR-3`),
test cases, commit messages and verification evidence quote the id, never the
wording - two copies of a sentence drift, a citation cannot.

Ids are permanent: never renumber, never reuse. A rule that stops applying stays
in place, marked `(deprecated in <change-id>)`, because older specs and tests
still cite it. Permissions share the same counter.

## 1. Route every request before writing code

### Locate

Find the capability the request is about in `.okf/index.md`, `.okf/features/`
and `openspec/specs/`. Read its entry and name the `BR-n` ids the request
touches. If `openspec/changes/` already holds an active change on that
capability, continue it instead of opening a second one.

### Decide

One question decides the route:

> Does this change make the OKF entry or a spec say something different - a
> term, a rule, a permission, a workflow, a scenario?

| Route | When | What to do | Knowledge |
| --- | --- | --- | --- |
| **Direct** | No: typo, formatting, comments, config, a non-breaking dependency bump, a refactor that keeps behavior, a test for behavior that already exists | Edit the code | Unchanged. If files moved, update `code_paths` in the affected entry |
| **Quick fix** | No: the code breaks a `BR-n` the entry already states correctly | Write a regression test, run it and see it fail, then fix the code | Unchanged - the knowledge was already right |
| **Rule tweak** | Yes, but small - every condition below holds | Edit in this order: the `BR-n` in the entry, the requirement in `openspec/specs/<capability>/spec.md`, a test that fails against the old code, the code. Then append a Verification History row to the entry | Updated in place, no change directory |
| **Full** | Yes, anything else: a new feature, a new `BR-n`, a new scenario, a behavior change, a bug the entry is silent or wrong about | `openspec-explore` while the idea is still vague, then `openspec-propose` -> `openspec-apply-change` -> verification pass -> `openspec-archive-change` | Created or enriched, then verified |

A **Rule tweak** is allowed only when all of these hold:

- exactly one existing `BR-n`, in one entry, changes;
- no new `BR-n` and no new scenario;
- the entry is not `criticality: high` (auth, permissions, money, customer data);
- no other capability is affected.

When two routes both seem to fit, take the heavier one. Too heavy costs minutes;
too light lets the knowledge drift silently.

### Announce

Before starting, state the route in one line, with its basis:

    Route: rule tweak - capability order-limit - BR-3 says "at most 5 items", the request makes it 10

A route with no entry or rule to cite as its basis is not yet a short route.
For a capability with no domain knowledge, say what makes it so:
`Route: direct - no domain knowledge: build script only`.

Put the same route in the commit message (`Route: quick-fix (order-limit BR-3)`),
so a reviewer can compare it against the diff.

### Escalate when a short route stops fitting

Stop and switch to a heavier route as soon as any of these appear:

| Signal | Means |
| --- | --- |
| An assertion in an existing test has to change | Behavior changed - not Direct, not Quick fix |
| A new test asserts something no `BR-n` or scenario states | You are defining behavior - Full |
| The entry is silent about, or contradicts, what you are changing | The knowledge is wrong or missing - Rule tweak or Full |
| The diff reaches into another capability's `code_paths` | Wider than planned - Full |
| A Rule tweak needs a second `BR-n` or a new scenario | Not a tweak - Full |

Never skip a route silently. If the user asks to bypass it, say which step is
skipped and which entry will no longer match the code, and let them decide.

### Test-first holds on every route that changes behavior

A test that covers new or changed behavior is written and seen failing on its
assertion before the code that makes it pass. When code and a pre-written test
disagree, the code is wrong by default. A test changes only when the entry or
spec changed first, or when the test has a mechanical defect (wrong fixture,
typo, bad assertion syntax). The order of repair when a rule turns out wrong is
always: OKF entry -> spec -> test -> code.

## 2. Naming

An OKF entry is named after the **capability**, never the change:
`.okf/features/<capability>.md`, matching `openspec/specs/<capability>/`.
`add-user-auth`, `fix-auth-mfa` and `improve-login` all belong to `user-auth`.
Enrich an existing entry rather than creating a near-duplicate.

## 3. Explore

`openspec-explore` does not read the schema, so this part lives here. Offer,
never auto-capture.

When the conversation settles on one concrete, nameable capability that has
domain knowledge - any of: terms, actors, roles, entities, permissions,
workflows, rules - ask: "Save what we discussed to OKF as unverified?"

- If yes: find an existing entry first, then create or enrich
  `.okf/features/<capability>.md` from `.okf/templates/feature.md.tmpl` with
  `verification_state: unverified`, quoting the original request as its source.
  Give new rules the next `BR-n`. Delete template sections you have no content
  for. Add or update its row in `.okf/index.md`.
- If no: keep exploring, and do not ask again until a different capability
  emerges.
- A capability with no domain knowledge (scaffolding, build tooling, a log
  format) gets no entry; say what makes it domain-free.

A question the entry already answers is not asked again - cite the `BR-n`. The
entry's Assumptions and Open Questions are what should generate questions.

An architectural decision that will outlive the change belongs in `design.md`
when the change is proposed; the verification pass promotes it to
`.okf/decisions/`. Explore never writes `.okf/decisions/` itself.

## 4. The full route

The schema carries the instructions for each artifact: `okf-link`, `proposal`,
`specs`, `design`, `test-cases`, `test-plan`, `tasks`, `verification`. OpenSpec
refuses `apply` until `okf-link`, `test-plan` and `tasks` exist.

`openspec-verify-change` and `openspec-archive-change` run generic logic, so the
OKF verification pass is an explicit step: follow the `verification` artifact
instruction in the schema whenever verify is invoked, and always before archiving
a change that has an `okf-link.md`. In short, for every linked entry:

1. Find evidence in the code for each `BR-n` the change touches - a real
   `file:line` or a test name - and give it a verdict:
   - `match` - nothing to do;
   - `okf-gap` - code right, entry stale: update the entry;
   - `code-gap` - entry right, code wrong: fix the code, never the entry;
   - `conflict` - ask the user; only this may end in `needs-revision`.
2. Set `verification_state` and `verified_at`, fill `code_paths`, remove the
   change id from `pending_changes`, append a Verification History row.
3. Promote durable decisions from `design.md` to `.okf/decisions/`.
4. Update `.okf/index.md`, then run the self-check below.

If the pass has not happened, warn and get explicit confirmation before
archiving anyway. Do not skip it silently.

## 5. Self-check

There is no validator; check by reading, after any edit under `.okf/` and before
archiving:

- every row in a change's `okf-link.md` points at a file that exists, or says
  `no domain knowledge - <reason>`;
- each entry's frontmatter has `type`, `title` (equal to the file name),
  `description`, `status`, `verification_state`, `criticality`;
- a `verified` entry has `verified_at` and non-empty `code_paths`, and every
  `code_paths` glob still matches a file;
- `BR-n` ids are unique within the entry;
- `pending_changes` names only active changes, and no longer names a change
  that is being archived;
- no `<placeholder>`, empty table row or bare `-` bullet is left in an entry;
- `.okf/index.md` lists every entry with its current state.
