# Summary

The test-first gate is the half of this workflow that decides *when* a test may
be written, not what it asserts. Its whole value is ordering: a test authored
before the code it guards can still refute that code, and a test authored after
it can only describe it. Everything else in the gate — the four-word status
vocabulary, contract stubs, the Known Gaps ledger — exists to make that ordering
observable to someone reading the change months later.

The gate is expressed in two places that must agree: the `tasks.md` group order,
which is what an agent actually executes, and the `test-plan.md` tables, which
are what a reviewer reads. When the two disagree, the executed order wins and
the plan quietly becomes fiction — so the gate is only as strong as the weaker
of the two.

# Business Rules

| ID | Rule | Source |
| --- | --- | --- |
| BR-1 | The test status vocabulary is exactly `planned`, `skeleton`, `failing`, `passing`. Any other word is an error, because a private vocabulary makes the tables unreadable to every consumer but their author. | workflow-doc |
| BR-2 | `planned` and `skeleton` differ by exactly one fact: whether the test file exists. A row that claims `skeleton` while no file exists is a false claim of progress, not a rounding error. | workflow-doc |
| BR-3 | A unit test covering a business rule MUST reach `failing` on its assertion — not on a missing import or a type error — before its implementation task starts. Contract stubs exist to make that reachable; a stub containing logic has already lost the gate. | workflow-doc |
| BR-4 | Every test the change plans MUST have its file authored before implementation starts: unit tests in the red state, integration and E2E tests at least as skeletons. After implementation a test may only be promoted from an existing skeleton — implementation MUST NOT be the step that first creates a test file, because a test born after the code it covers was shaped by that code. | review-2026-08-02 |
| BR-5 | A test row still at `skeleton` or `planned` when archive readiness is assessed MUST appear in the test-plan Known Gaps with a reason and a named owner. A skeleton that survives into the archive unowned is an untested requirement wearing a test's name. | workflow-doc |
| BR-6 | A test-plan MUST record each test's status as of the moment implementation started, separately from its current status. Overwriting the initial status with the final one destroys the only evidence that the ordering rules were followed, and leaves an all-`passing` table that a test-last change produces identically. | review-2026-08-02 |
| BR-7 | Any artifact that instructs an agent to promote a skeleton MUST be preceded by an artifact instruction that creates it. A workflow that presupposes an input nothing produces will be resolved by the agent improvising, and the improvisation will land wherever is cheapest — after the code. | review-2026-08-02 |
| BR-8 | When the implementation and a pre-written test disagree, the implementation changes. A pre-written test MAY be changed on exactly two grounds: the OKF entry or spec it encodes changed first, or the test has a mechanical defect (wrong fixture, typo, bad assertion syntax). "The code turned out to work differently" is not a ground — it is the disagreement the test exists to report, and editing the test to end it discards the only finding the test ever produced. | review-2026-08-02-tdd-direction |
| BR-9 | Every change to a pre-written test after implementation started MUST be recorded with the ground it stands on, and the record MUST name it: the `BR-n` or spec that changed, or the specific mechanical defect. A test change with no stated ground is indistinguishable from a test fitted to the code, so an unrecorded one is treated as the latter. | review-2026-08-02-tdd-direction |
| BR-10 | When implementation reveals that a business rule must be different, the order of repair is fixed: amend the OKF entry, then the spec that cites it, then record the change, then the test, then the code. Reversing any step lets the code define the domain, which is the failure the whole knowledge base exists to prevent. | review-2026-08-02-tdd-direction |

# Workflows

## Primary Workflow

1. Declare the contracts the planned unit tests need — types, signatures, routes
   that return 501 — with bodies that only throw (BR-3).
2. Write the business-rule unit tests against those stubs, run them, and record
   the actual assertion failure as each one's initial status (BR-3, BR-6).
3. Author the integration and E2E test files as skeletons, declared with the
   runner's pending mechanism, and record `skeleton` as their initial status
   (BR-4, BR-6).
4. Implement until the unit tests go green.
5. Promote the skeletons to executable specs and make them pass (BR-4).
6. Before archive, give every row still at `skeleton` or `planned` a reason and
   an owner in Known Gaps (BR-5).

Throughout steps 4 and 5 the tests are fixed and the code moves (BR-8).

## Alternative Or Failure Workflows

- **The harness for a level does not exist yet.** The skeleton is still authored
  at step 3 and stays `skeleton` through step 5, ending in Known Gaps with an
  owner (BR-4, BR-5). Deferring the harness is legitimate; deferring the file is
  what BR-4 forbids.
- **A level genuinely does not apply.** Its task group is dropped and the reason
  is stated in test-plan.md. Silence — an empty group, or a level that simply
  never appears — is not that reason.
- **The implementation contradicts a pre-written test.** The default is that the
  code is wrong and gets fixed (BR-8). If the rule itself turns out to be wrong,
  the repair runs upstream first — entry, then spec, then the record, then the
  test, then the code (BR-10) — and the test change is recorded with its ground
  (BR-9). What must never happen is the test being edited first and the reason
  reconstructed afterwards, because by then the disagreement it reported is gone.
- **A pre-written test has a mechanical defect.** It is fixed and recorded as
  such (BR-9). The distinction that matters: a mechanical fix leaves the claim
  the test makes unchanged, so if the assertion moves, this was not one.

# Risks And Compliance Constraints

| Risk Or Constraint | Impact | Mitigation Or Handling |
| --- | --- | --- |
| A test file first created after the implementation it covers | The test can only confirm what the code already does; the change reads as tested while nothing was ever refuted | BR-4 places the file before implementation; BR-6 makes a violation visible after the fact |
| A finished test-plan showing every row `passing` | Identical to what a test-last change produces, so a reviewer cannot tell the two apart | BR-6 keeps the initial status alongside the current one |
| A test quietly rewritten until it agrees with the code | The change reads as test-first while the tests were fitted to the implementation - the exact failure mode BR-4 and BR-6 do not reach, because the file existed and the statuses are honest | BR-8 fixes the direction of adaptation, BR-9 requires every test change to carry its ground, and the record is checked rather than trusted |

# Assumptions

- The runner used by a downstream project has some pending mechanism
  (`it.todo`, `test.todo`, `test.fixme`, or an equivalent) that compiles and
  lints clean. A runner without one cannot express `skeleton`. This kit's own
  harness had no such mechanism until `skeleton-tests-before-implementation`
  added `todo()` to `test/run.mjs`, which is what a project in that position
  should do rather than waiving the level.
